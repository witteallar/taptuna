# Техническое задание: «Лаборатория протоколов»

## 0. Что меняем относительно исходного ТЗ

**Границы scope (что НЕ делаем):**
- Расшифровка TLS, разбор сжатия, поддержка IPv6 и не-Ethernet канального уровня.
- Автоматический вывод протокола без участия человека.
- Автоматическое связывание запрос↔ответ (только ручная разметка + простое эвристическое сопоставление).

---

## 1. Что должно получиться в итоге

**Один пользователь, один ПК, браузер = GUI.**

```
┌────────────────────────────────────────────────────┐
│  main.py  →  Flask на 127.0.0.1:5000  →  Browser   │
│                                                    │
│  Пользователь делает всё через веб-интерфейс:      │
│   • открывает .pcap/.pcapng                        │
│   • выбирает TCP-сессию и направление              │
│   • видит восстановленный поток в hex-вьювере      │
│   • размечает границы сообщений                    │
│   • строит интерпретацию (поля, типы)              │
│   • применяет её к корпусу                         │
│   • видит контрпримеры                             │
│   • сохраняет проект (.tlproj)                     │
│   • экспортирует отчёт (.md) и модель (.json)      │
└────────────────────────────────────────────────────┘
```

Консоль используется **только** для запуска `python main.py`. Все ошибки — в GUI (тосты/модальные окна).

## 2. Стек и обоснование

| Слой | Технология | Зачем именно так |
|---|---|---|
| Разбор PCAP | **tshark** (CLI) + **pyshark** | pyshark даёт доступ к полям tshark-а как к объектам; `tcp.stream`, `tcp.seq`, `tcp.len` — уже готовые. |
| TCP-реассемблинг | собственная реализация на Python | Нужен полный контроль над retransmission, out-of-order, gap. `tshark -z follow,tcp,raw` не отдаёт per-packet привязку. |
| Backend | **Flask** | Лёгкий, синхронный, идеально для локального API. |
| Frontend | **HTML + CSS + vanilla JS** | Без сборщиков, без node.js — запускается «из коробки». |
| Хранение проекта | **ZIP-контейнер** `.tlproj` | Переносимость, один файл, включает исходный pcap. |
| Тесты | **pytest** | Быстро, стандартно. |

**requirements.txt:**
```
Flask==3.0.3
pyshark==0.6
pytest==8.3.2
```

**Системная зависимость:** `tshark >= 4.0` (проверяется при старте `main.py`, если нет — показать ошибку в браузере).

### 3.1. Пояснения по каждому значимому файлу (вход → выход)

#### `main.py`
- **Вход:** аргументы CLI (опционально `--port`, `--no-browser`).
- **Выход:** запущенный Flask + открытый браузер. При повторном запуске — понятная ошибка «порт занят».
- **Что делает:** проверяет tshark → создаёт Flask → `webbrowser.open("http://127.0.0.1:5000")` → `app.run()`. Никакой логики анализа здесь нет.

#### `config.py`
- **Вход:** —
- **Выход:** модуль-константы: `MAX_FILE_SIZE=100MB`, `MAX_PACKETS=250_000`, `HOST`, `PORT`, `PROJECT_VERSION="1.0"`, `TSHARK_TIMEOUT=60`.

#### `backend/services/pcap_service.py`
- **Вход:** путь к `.pcap/.pcapng`.
- **Выход:** `List[Session]` — список TCP-сессий.
- **Логика:** через `pyshark.FileCapture(..., use_json=True, include_raw=True)` итерируется; группировка по 4-tuple + проверка на разные соединения по времени/SYN-флагам (переиспользование портов ≠ одна сессия).
- **Использует:** `tshark` под капотом.

#### `backend/services/tcp_service.py`
- **Вход:** путь к pcap + `Session`.
- **Выход:** `ReassembledStream` для каждого направления — `bytes` + `List[ByteChunk]`, где `ByteChunk` = `{seq, data, packet_number, direction}`.
- **Логика:**
  1. Собрать все пакеты сессии.
  2. Для каждого направления: сортировка по `tcp.seq`, обработка retransmission (одинаковые seq+len+data → игнор), обработка overlap (политика «первый победил», политика настраивается в config), поиск gaps → создание `ByteChunk` с флагом `is_gap=True`.
- **Важно:** границы восстанавливаем по seq, а не по порядку в файле.

#### `backend/services/framing_service.py`
- **Вход:** `ReassembledStream`, набор «правил фрейминга» (искомый маркер, length-префикс).
- **Выход:** `List[Message]` с `start_offset`, `end_offset`, `raw_bytes`.
- **Логика:**
  - **ручной режим:** пользователь в UI кликает «здесь граница»;
  - **автоматический:** поиск повторяющегося байтового маркера + правило «N байт длины после маркера»; результат помечается `source="auto"` и подсвечивается как непроверенный.

#### `backend/services/interpretation_service.py`
- **Вход:** `bytes` (сообщение или весь поток) + `Interpretation`.
- **Выход:** `List[FieldValue]` = `{field_name, offset, raw_bytes, decoded_value, type}`.
- **Логика:** последовательное применение правил (offset/size/type/endianness). Типы: `uint8/16/32`, `int8/16/32`, `ascii`, `hex`, `bytes`, `bcd`, `bitfield`.
- **Обработка ошибок:** если правило выходит за границы — `FieldValue` с `error="out_of_bounds"`, не исключение.

#### `backend/services/project_service.py`
- **Вход (save):** текущее состояние (путь к pcap, список сессий, интерпретации, разметки, комментарии).
- **Выход (save):** `.tlproj` — ZIP-архив:
  ```
  project.tlproj
  ├── meta.json          ← версия, дата, автор
  ├── capture.pcap       ← копия исходника
  ├── sessions.json      ← список сессий
  ├── annotations.json   ← разметки границ, комментарии
  ├── interpretations/   ← папка с *.json правилами
  └── checks/            ← результаты проверок
  ```
- **Вход (load):** `.tlproj` → распаковка в `data/projects/<uuid>/` → восстановление состояния.
- **Требование:** относительные пути внутри архива — проект переносится между машинами.

#### `backend/services/report_service.py`
- **Вход:** проект.
- **Выход:** `report.md` (человекочитаемый) + `interpretation.json` (машиночитаемый) + `apply.py` (скрипт для применения к новому pcap).
- **Report.md содержит:** описание источника, список сессий, интерпретацию, примеры срабатываний, контрпримеры, открытые вопросы.

#### `backend/routes.py` — HTTP API (см. §4).

#### Frontend JS
- `api.js` — единая обёртка `fetch` с обработкой ошибок.
- `sessions.js` — таблица сессий, выбор направления.
- `stream.js` — hex-вьювер с подсветкой разметки, обработка клика по байту (для offset).
- `interpretation.js` — редактор правил (drag-n-drop полей или простая таблица).
- `corpus.js` — выбор нескольких сессий как «корпус», запуск проверки, отображение контрпримеров.
- `project.js` — save/load/export через файловые диалоги.

## 5. Формат интерпретации (ключевое решение)

Интерпретация — **декларативный JSON**, а не скрипт (для повторного применения и безопасности).

```json
{
  "name": "device_proto_v1",
  "version": "1.0",
  "applies_to": {
    "direction": "c2s",
    "min_size": 4
  },
  "rules": [
    {"field": "magic",   "offset": 0, "size": 2, "type": "hex"},
    {"field": "command", "offset": 2, "size": 1, "type": "uint8"},
    {"field": "length",  "offset": 3, "size": 2, "type": "uint16le"},
    {"field": "payload", "offset": 5, "size": "$length", "type": "bytes"},
    {"field": "crc",     "offset": "$end-2", "size": 2, "type": "uint16le"}
  ]
}
```

- `$length` — ссылка на ранее извлечённое поле.
- `$end-N` — от конца сообщения.
- Если правило не применимо к конкретному сообщению — оно помечается `not_applicable`, не падает.

Для сложной логики допускается второй формат — `rules_python.py`, но он помечается как «непереносимый без Python» и в отчёте это явно указывается.

## 6. План разработки на 7 дней (с использованием ИИ)

Предполагается: 1 разработчик + ИИ-ассистент. Реалистично уложиться, если не отвлекаться на перфекционизм UI.

### День 1 — Каркас и данные
- Скелет `main.py`, Flask, `/api/health`, проверка tshark.
- `pcap_service`: список сессий через pyshark.
- Минимальный фронт: открыть файл, показать список сессий.
- **Артефакт:** можно открыть pcap и увидеть сессии.

### День 2 — TCP-реассемблинг
- `tcp_service`: сортировка по seq, retransmission, gaps.
- Тесты на синтетическом pcap (сгенерировать scapy-скриптом).
- Простейший hex-вьювер в UI.
- **Артефакт:** видно восстановленный поток байтов.

### День 3 — Фрейминг
- `framing_service`: ручная разметка + авто по маркеру.
- UI: подсветка границ, клик по байту → offset в буфер.
- **Артефакт:** можно разметить границы сообщений.

### День 4 — Интерпретация
- `interpretation_service`: правила JSON, типы полей.
- UI: редактор правил (таблица полей).
- Подсветка полей на hex-вьювере.
- **Артефакт:** видно разобранные поля сообщения.

### День 5 — Проверка на корпусе + проект
- `corpus/check` API, отображение контрпримеров.
- `project_service`: save/load `.tlproj`.
- **Артефакт:** проект сохраняется и открывается.

### День 6 — Отчёт и полировка
- `report_service`: `report.md` + `interpretation.json` + `apply.py`.
- Обработка ошибок (неполные данные, битые pcap).
- Тесты `pytest`.
- **Артефакт:** экспорт отчёта работает, тесты зелёные.

### День 7 — Демонстрация и документация
- README с запуском.
- Записать демо-сценарий на реальных данных.
- Измерение памяти/времени на нагрузке из §10 исходного ТЗ.
- **Артефакт:** готовый проект + демо.

## 7. Критерии приёмки (проверяемые)

1. **R1.** Открывается `.pcap` и `.pcapng`; для сессии с retransmission прикладные байты не дублируются; есть кнопка «показать пакет-источник» → открывается окно с номером пакета.
2. **R2.** Hex-вьювер: выделение диапазона, копирование hex, поиск по байтам.
3. **R3.** Интерпретация в JSON применяется ко **всем** сообщениям сессии; если правило неприменимо — отображается явно.
4. **R4.** Кнопка «Проверить корпус» → отчёт со списком: сколько сообщений подошло, где нарушено, где gap.
5. **R5.** `.tlproj` открывается на другой машине (проверяется вручную в Docker-контейнере).
6. **R6.** `apply.py` из отчёта запускается на новом pcap без GUI и выдаёт `results.json`.
7. **Производительность:** 100 МБ pcap, 250k пакетов — открытие ≤ 90 с, применение интерпретации ≤ 10 с (на 4 vCPU / 8 ГБ).

## 8. Явные ограничения (зафиксировать в README)

- Только TCP/IPv4 над Ethernet.
- Только незашифрованный трафик.
- Один capture за раз.
- Нет автоматического вывода семантики — только декларативные правила от исследователя.
- Retransmission с разными данными (патология) — предупреждение, не разрешается автоматически.
