# ТЗ: «Лаборатория протоколов» — v3.0 (final)

## 0. Роль и цель

Ты — senior full-stack + systems engineer. Реализуй офлайн-инструмент
«Лаборатория протоколов» для исследования недокументированного бинарного
обмена поверх TCP/IPv4 по записям PCAP/PCAPNG.

Стек: Python 3.11+ (Flask, SQLite) + нативное ядро на Rust (PyO3).
tshark вызывается только через subprocess(shell=False).
GUI — локальный веб-интерфейс на 127.0.0.1:5000.

Задача инструмента: инженер открывает запись, восстанавливает прикладной
поток, формулирует и проверяет гипотезы о структуре сообщений, находит
контрпримеры, сохраняет/переносит/воспроизводит исследование, экспортирует
читаемый отчёт и машиночитаемую интерпретацию.

Основной сценарий — офлайн. Сеть в рантайме не нужна.

## 3. Глоссарий (обязателен в коде, БД, UI)

- **Запись трафика** — исходный PCAP/PCAPNG, read-only, sha256.
- **Сессия** — экземпляр TCP-соединения (5-tuple). Реюз портов не сливает.
- **Направленный поток** — байты одного направления, восстановленные по seq.
- **Фрейминг** — выделение прикладных сообщений из потока. Граница
  TCP-пакета не определяет границу сообщения.
- **Интерпретация** — правило/модель/скрипт, извлекающий структуру/значения.
- **Гипотеза** — предположение о структуре/назначении, связанное с
  наблюдениями и основаниями.
- **Корпус** — выбранный набор записей/сессий для проверки.
- **Контрпример** — данные, где правило не выполняется.
- **Наблюдение (Observation)** — то, что видно в байтах.
- **Правило (Rule)** — то, что извлекла интерпретация.
- **Гипотеза о назначении (Hypothesis)** — предположение о смысле.
- **Журнал действий (Action Log)** — хронология действий над устройством
  с параметрами и наблюдаемым результатом.

## 4. Архитектура и фазы

Browser (127.0.0.1:5000)
  ↕ HTTP + SSE
Flask backend (REST, SSE, jobs, project model, interpreter, verification, reports)
  ↕ subprocess(shell=False)
tshark CLI (ingest — один проход; point-lookup — JSON на frame)
  ↕
SQLite + content-addressed storage (blobs/<sha256>.bin)
  ↑
taptuna._native (Rust): reassembly, framing, declarative extractor, safe-eval


**Фаза 1 (cold ingest):** один вызов tshark на файл → строки полей →
нативное ядро делает reassembly → SQLite + CAS. Результат фазы 1 —
единственный источник истины для фазы 2.

**Фаза 2 (warm):** UI, интерпретации, verification, reports работают
только с локальной моделью. tshark дёргается точечно: `-T json` на один
frame; follow-stream — только визуализация, помечена в UI как
«не источник истины».

**Семантика времени:** `frame.time_epoch` — время наблюдения в точке
захвата. Все временные характеристики результата (start/end сессии,
таймлайн, сравнение с журналом действий) наследуют эту семантику; это
явно фиксируется в UI и отчёте.

## 5. Инварианты (проверяются тестами)

- **I1.** Исходный PCAP read-only, идентифицируется по sha256.
- **I2.** Любой результат ссылается на `(source_id, byte_range)`.
- **I3.** `known` / `unknown` / `ambiguous` различимы в модели, API, UI.
- **I4.** Observation ≠ Rule ≠ Hypothesis — три таблицы, разные API.
- **I5.** Смена правил не переодевает старые результаты; stale вычисляется
  при чтении и никогда не удаляет старые прогоны.
- **I6.** Долгие операции — jobs с SSE-прогрессом и отменой. tshark:
  `terminate()` → 5 с → `kill()`. Sandbox: `kill()` + пометка мёртв.
- **I7.** Проект переносим: относительные пути везде, включая ref-режим
  (ref-путь хранится относительно `TAPTUNA_REF_ROOT`).
- **I8.** Детерминизм. Одинаковый вход + версия интерпретации + seed →
  байт-в-байт одинаковый `result_hash`. Reassembly детерминирован по
  `(abs_seq, frame_number)`.

## 6. R1. Работа с исходным обменом

### 6.1. Приёмка
- Открытие PCAP и PCAPNG (single-interface Ethernet+IPv4+TCP) без
  промежуточного формата.
- Список сессий: 5-tuple, пакеты, байты, start/end, `tcp.stream`.
- Выбор сессии и направления (`a_to_b`, `b_to_a`).
- Восстановление прикладного потока **собственным кодом** поверх полей
  tshark.
- Обратный переход offset → frame (byte_map).
- Ошибка одной сессии не блокирует остальные.

### 6.2. Ingest — ровно один вызов tshark на файл

tshark -r <pcap> \
  -T fields -E separator=\t -E occurrence=f \
  -e tcp.stream \
  -e frame.number -e frame.time_epoch \
  -e ip.src -e ip.dst -e tcp.srcport -e tcp.dstport \
  -e tcp.seq -e tcp.ack -e tcp.len \
  -e tcp.flags.syn -e tcp.flags.ack -e tcp.flags.fin -e tcp.flags.rst \
  -e tcp.payload \
  -o tcp.check_checksum:FALSE \
  -o ip.defragment:FALSE \
  -o tcp.desegment_tcp_streams:FALSE

Список сессий формируется из этих же строк (группировка по `tcp.stream`).
`ip.defragment:FALSE` — потому что вход без фрагментации (см. §2); при
встрече фрагмента — предупреждение в логе, попытки склейки нет.

**Запрещено:**
- `shell=True`.
- `-Y tcp.stream==N` отдельным вызовом на каждую сессию.
- `-T json` на весь файл ради списка сессий.
- `follow,tcp,raw` как источник прикладного потока.
- tshark на каждое действие UI (кроме point-lookup одного frame).
- Парсинг `tcp.flags` как hex/dec — неоднозначно в разных сборках;
  SYN/ACK/FIN/RST берём отдельными полями.
- Абсолютные пути к tshark внутри проекта.

### 6.3. Вызов tshark
- `subprocess.Popen([...], shell=False)`.
- Путь: `TAPTUNA_TSHARK` или `PATH`.
- `tshark -v` фиксируется в манифесте; расхождение при открытии проекта —
  предупреждение с опцией re-ingest.
- Таймаут, лимит вывода, отмена — настраиваемые, с явной ошибкой при
  превышении (без скрытого усечения).
- `stderr` вычитывается всегда (иначе дедлок на 64 КиБ).
- Point-lookup (`-T json` на frame) выполняется вне hot-path Flask-worker.

### 6.4. Правила reassembly
- Абсолютный seq по RFC 9293. Опорная точка — **максимальный непрерывный**
  seq, не последний увиденный. ISN берётся из SYN, если он есть.
- Сортировка сегментов по `(abs_seq, frame_number)` — обязательно для
  детерминизма.
- Одинаковые ретрансмиссии дедуплицируются, исходные пакеты сохраняются.
- Различающиеся перекрытия → `Ambiguity` + политика
  `first_wins | last_wins | halt_and_mark` (по умолчанию `first_wins`,
  фиксируется в манифесте и per-direction).
- Пропуск/усечение → `Gap`, байты помечены `unknown`, zero-fill
  запрещён.
- `tcp.len == 0` не создаёт сегмент.
- Отсутствие SYN → `roles_established = false` (без домыслов).
- Wraparound seq обрабатывается по RFC 9293 (окно ±2^31 от опорной точки).
- Одна система координат: `byte_map` — offsets относительно stream_start;
  `abs_seq` — внутренняя деталь.

## 8. R3. Интерпретации

### 8.1. Формат
YAML/JSON, `schema_version: 1`. Декларативный **или** script
(`decode(msg, ctx)`), ровно одно. Общие блоки `framing`, `constraints`,
`semantics`.

### 8.2. Framing
`length_prefix | delimiter | fixed | regex`.
Валидация: `header_size ≥ offset + size`; `value ∈ {payload, total}`;
`max_message` обязателен.

### 8.3. Поля
Типы: `u8/i8/u16be/u16le/i16be/i16le/u32be/u32le/i32be/i32le/u64be/u64le/i64be/i64le/bytes/ascii/utf8/ipv4/mac/bcd`.
Выражения `offset`/`size`: AST-whitelist, имена `len/header_size/max_message`,
арифметика `+ - * / // %`. `size: remaining` — до конца сообщения.

### 8.4. Контракт движков
Оба движка (declarative и script) возвращают per message:
`{index, stream_offset, length, message_name, status, fields, notes,
unknown_ranges}`.
`status ∈ ok | partial | no_match | unknown_frame`.

### 8.5. Sandbox (для script)
- Отдельный процесс.
- **Один долгоживущий worker на job** (не на direction).
- Rlimits: `RLIMIT_CPU`, `RLIMIT_AS` (default 512 MiB), `RLIMIT_FSIZE=0`.
  `RLIMIT_NPROC` **не трогать**.
- Import whitelist (`math`, `struct`, `binascii`, `re`, `dataclasses`,
  `typing`, `collections`, `json`, `decimal`, `fractions`, `enum`,
  `itertools`, `functools`, `operator`, `string`, `textwrap`).
- `random` детерминирован с seed.
- `stderr` вычитывается родителем.
- Таймаут → `kill()` + respawn + пометка клиента «мёртв». Никогда не
  переиспользовать worker после таймаута.

### 8.6. Приёмка
- Применение к нескольким примерам, включая различающиеся параметры и
  размеры данных.
- Применение к новой записи в области действия без ручного описания
  каждого примера.
- Частичное описание: `unknown`-области различимы в UI.
- Явное разделение «получено по правилам» и «предположение о назначении».

## 9. R4. Проверка и уточнение

### 9.1. Корпус
Явные критерии: `captures` (sha256), `a_ports`, `b_ports`, `any_ports`,
`has_syn`, `min_packets`, `min_bytes`, `directions`. Без ролевой магии
(никаких «server/client» без SYN).

### 9.2. Классификация сообщения
- `violation` — error-constraint упал.
- `ambiguous` — сообщение пересекает ambiguous-регион byte_map.
- `incomplete` — `partial`, `unknown_frame`, пересечение с `unknown`-
  регионом.
- `ok` — всё сошлось.
- `not_applicable` — интерпретация не применима к сессии.

Вердикт прогона: `violation > ambiguous > incomplete > ok > not_applicable`.

### 9.3. Приёмка
- Сводка по корпусу: разобрано, нарушений, неполных, неоднозначных,
  неприменимых, неизвестных.
- Переход от любого пункта сводки к исходным данным.
- Повторный прогон после изменения интерпретации; устаревшие результаты
  помечены stale.
- Фильтрация корпуса — с видимыми условиями.
- Запрещено выдавать совпадение на подмножестве за универсальность;
  `not_applicable` при 0 ok отображается явно.

## 12. Нативное ядро (Rust)

### 12.1. Что в нём
- reassembly,
- framing (все 4 стратегии),
- декларативный экстрактор полей,
- safe-eval выражений и предикатов (constraints).

### 12.2. Что в Python
- subprocess tshark и разбор строк;
- SQLite/store; Flask; jobs/SSE;
- script-sandbox;
- отчёты;
- журнал действий.

### 12.3. Интерфейс
PyO3-биндинг `taptuna._native`. Fallback — чистая Python-реализация под
флагом `TAPTUNA_NATIVE=0`. Тесты гоняются на обоих; результаты
байт-идентичны.

### 12.4. Сборка
Dev: `maturin develop`. Релиз: prebuilt wheels linux-x86_64.
Без Rust-тулчейна — автоматический fallback с предупреждением в UI.

### 12.5. Wire-парсер (дополнительно к reassembly)
Собственный парсер Ethernet + IPv4 + TCP в Rust — для тестов без tshark,
для проверки tshark на выборке (oracle), для офлайн-использования.
Требования:
- Поддержка одного VLAN-тега (802.1Q, 802.1ad).
- Отказ на IP-фрагментах (предупреждение, не склейка).
- Проверка `IHL ≥ 5`, `data_offset ≥ 5`, `total_len ≥ ip_hdr_len`.
- Обрезка по `ip.total_len` для отсечения padding.
- Возврат `Ok(None)` для не-IPv4/не-TCP (не ошибка), `Err` для
  распознанных, но повреждённых.

### 12.6. Seq tracker
- Опорная точка — максимальный непрерывный seq, не последний увиденный.
- Seed из SYN, при отсутствии — из минимального наблюдённого seq.
- Окно ±2^31 от опорной точки.
- Обновление опорной точки — только при подтверждённой непрерывности.

### 12.7. Приёмка
- Native и Python дают одинаковый `result_hash` на корпусе.
- Property-тесты (перестановки, дубли, перекрытия, wraparound).
- Fuzz на `frame()` без паник.
- Bench: ingest 100 МиБ ≤ 90 s; verify 100k сообщений ≤ 60 s.

## 14. Модель данных (SQLite)

Таблицы: `captures`, `sessions`, `directions`, `stream_segments`,
`packets`, `interpretations`, `corpora`, `verification_runs`,
`verification_results`, `observations`, `hypotheses`,
`hypothesis_observations`, `action_log`, `meta`.

Требования:
- `PRAGMA user_version` + мигратор.
- Индексы: `vres(run_id, status)`, `vres(run_id, id)`,
  `sessions(capture_id, stream_index)`, `interp(name, version DESC)`,
  `seg_dir_offset`, `obs(target_type, target_id)`.
- Payload > 4 КиБ — в CAS (`blobs/<sha256>.bin`); inline ≤ 4 КиБ.
- Порог inline — в манифесте, смена = новая версия ingest.
- `directions.gaps_json`, `directions.ambiguities_json` — JSON-столбцы.

Stale: вычисляется при чтении по:
- версии интерпретации (`superseded by name@N+1`);
- drift политик (`overlap`, `checksum` — snapshot в `params_json`).

### 16.1. UX-требования
- Неизвестные и неприменимые данные визуально отличимы от разобранных.

- Любая ячейка / значение кликабельны → переход к байтам источника.
- Прогресс и «Отмена» для всех долгих операций.
- Follow-stream в UI помечен «не источник истины».
- Hex-вьюер использует виртуальный скролл для потоков > 1 МиБ.
- Jump-to-offset по клику в таблице результатов и в diff.

## 17. Нефункциональные требования

### 17.1. Нагрузка
- ≤ 100 МиБ PCAP
- ≤ 250 000 пакетов
- ≤ 1 000 TCP-соединений
- ≤ 100 000 сообщений
- короткие команды и переменные ответы до 64 КиБ
  (**профиль измерения, не ограничение формата**)

### 17.2. Производительность
- Ingest 100 МиБ ≤ 90 s (один проход tshark + нативное ядро).
- Verify 100k сообщений ≤ 60 s.
- Пиковая RSS backend ≤ 2 ГиБ.
- Уже загруженные данные остаются доступны при длительных операциях.

### 17.3. Надёжность и ресурсы
- Защитные пределы: `max_stream_bytes`, `max_output_bytes`, `timeout`.
- При превышении — явная ошибка, **без скрытого усечения**.
- Логирование времени и пиковой памяти per job.
- Ошибки и неподдерживаемые данные диагностируются; источник не
  изменяется; неизвестное не подменяется.

### 17.4. Воспроизводимость
- `result_hash` sha256 от канонизированного JSON.
- Недетерминизм (если есть) явно логируется с seed.
- Одинаковый вход + версия + настройки → одинаковый результат.

### 17.5. Автономность
- Основной сценарий — офлайн. Зависимости ставятся по инструкции.
- Сеть в рантайме не нужна.

| Ситуация | Требование | Тест |
|---|---|---|
| Переупорядочивание пакетов | байты по seq | property + unit |
| Одинаковая ретрансмиссия | без дублей, пакеты сохранены | unit |
| Пропуск / усечение | unknown, без zero-fill | unit |
| Разные данные в перекрытии | ambiguity + политика | unit × 3 политики |
| Недоступное начало | roles_established=false | unit |
| Checksum | политика фиксирована; offloading в отчёте | unit + report |
| Повторный импорт sha256 | явное предупреждение | unit |
| Разные соединения не сливаются | по 5-tuple + времени | integration |
| Ошибка одной сессии | не блокирует остальные | integration |
| Wraparound seq | склейка по RFC 9293 | property |

## 19. Проверяемость гипотез

- Три сущности: observation, rule, hypothesis.
- Каждая гипотеза хранит: формулировку, `observation_ids`, проверки,
  контрпримеры, статус.
- Изменение правила → обновление результатов или явная пометка stale.
- Успешный разбор структуры **не** подтверждает смысловую интерпретацию.
- UI: наблюдения и гипотезы — отдельные вкладки, не смешаны с rules.

## 20. Тесты и примеры

### 20.1. Unit
- reassembly: property-based (перестановки, дубли, перекрытия, wraparound).
- framing: 4 стратегии, resync, границы.
- декодеры: все типы, включая bcd / ipv4 / mac.
- safe-eval: арифметика, предикаты, отказ на disallowed nodes.

### 20.2. Integration
- Fake tshark (shell-script с заготовленным выводом) → ingest →
  sessions / segments / packets. Тест **считает** запуски tshark —
  должен быть ровно один на файл.
- Sandbox: whitelist, timeout, kill / respawn, stderr flood.
- Point-lookup в фоне (не в hot path).

### 20.3. Cross-validation
- Native vs Python: одинаковый `result_hash` на корпусе.
- Два прогона verify → идентичный `result_hash`.

### 20.4. E2E
- `examples/input/*.pcap` (включая дефектные) + `examples/expected/*.json`
  + `make test-examples`.

## 21. Anti-cheat

- Никакой подстановки ожидаемых ответов по имени файла или сигнатуре
  контрольного набора.
- Демонстрация заранее подготовленного описания (без применения к данным
  и повторной проверки) не считается результатом.
- Отчёт обязан явно указывать состав корпуса и область применимости;
  совпадение на подмножестве не выдаётся за универсальность.
